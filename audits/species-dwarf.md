# Species Audit: Dwarf

## Summary

No `race`-type item exists for Dwarf in the compendium (`raceItemExists: false`), only the 8 trait `feat` items — consistent with the pack-wide finding for all 9 core PHB species. Every trait's `effects`/`activities`/`advancement` are empty, but this is **not fully explained by staleness**: re-running the current (working-tree) detection pipeline against these exact 8 traits by hand shows real, still-open gaps. Two traits (**Darkvision**, **Dwarven Toughness**) would now be correctly detected if re-imported. The rest would still come back empty even today: **Dwarven Resilience** only half-detects (poison resistance yes, condition-save advantage no — and no detector for "advantage on saves" exists anywhere in the codebase), **Stonecunning**'s Tremorsense/limited-use bonus action is entirely outside current detector coverage, and — most significant — the species-level **Ability Score Increases** trait uses PHB-2024 species phrasing ("increase one score by 2 and a different one by 1...") that the ASI detector's regex does not recognize at all, since it only matches the feat/half-feat boilerplate phrasing ("increase one ability score of your choice by..."). This last gap is not Dwarf-specific — it would affect every core species' ASI trait identically — and isn't tracked by any of issues 001–019.

Note on repo state: `scripts/scraper.mjs`, `scripts/effects-builder.mjs`, and `scripts/importer.mjs` currently have uncommitted working-tree changes (`git diff --stat` shows +338/-37 lines) that already implement issues 016, 017, and 019 (`parseDcFormula`, `parseActivation`, `parseRangeAndTarget`, the relaxed spell-verb regex) — these are not yet committed to git (last commit `e160cc0` predates them) but they ARE what's on disk and what a live Foundry import would actually run. For Dwarf specifically these three issues turn out to be inert: Dwarf has no spellcasting, no DC clause, and no dice, so 016/017/019 change nothing about Dwarf's expected output. Issue 018 (Magic Initiate class narrowing) is unrelated to species entirely. Findings below evaluate "current code" as this actual on-disk state.

## Traits

### Dwarven Resilience
- **Prose:** "You have Resistance to Poison damage. You also have Advantage on saving throws you make to avoid or end the Poisoned condition."
- **Expected (current code):** The damage-resistance clause fires: `traitRe` in `scanSegmentText` (scripts/scraper.mjs:582-590) matches "Resistance to Poison damage" and produces an ActiveEffect change `{key: "system.traits.dr.value", mode: 2 (ADD), value: "poison"}`. The second sentence does **not** produce anything — there is no "advantage on saving throws" detector anywhere in scraper.mjs (confirmed via grep for "advantage", zero matches in the whole file). The self-grant/condition-immunity detectors (lines 611-710) require an explicit "have/has/gain/gains/are/become the X condition" or "immune to the X condition" phrasing; "advantage ... to avoid or end the Poisoned condition" matches neither, so it's correctly not misfired on, but it's also never captured as its own mechanic (dnd5e has no single stock ActiveEffect key for "advantage on saves vs. one specific condition" — this would need a custom flag or a `flags.midi-qol`-style key the module doesn't currently emit at all).
- **Actual (compendium data):** `effects: []` — confirms the empty-pack finding.
- **Gap / verdict:** Half-detected even on current code. The resistance half would build correctly on re-import; the advantage-on-saves half is a genuinely uncovered mechanic shape, not addressed by any of issues 001-019. Worth a new issue if this class of "advantage vs. condition" phrasing recurs elsewhere (it's common across several species — e.g. Gnome's mental-condition advantage, Halfling's frightened advantage).

### Stonecunning
- **Prose:** "As a Bonus Action, you gain Tremorsense with a range of 60 feet for 10 minutes. You must be on a stone surface or touching a stone surface to use this Tremorsense. The stone can be natural or worked. You can use this Bonus Action a number of times equal to your Proficiency Bonus, and you regain all expended uses when you finish a Long Rest."
- **Expected (current code):** Nothing is built. Walking through `scanSegmentText`: (1) the sense-grant loop (scripts/scraper.mjs:772-782) only recognizes `blindsight`/`truesight` by name — Tremorsense is never in that list, so it's structurally invisible even though the surrounding "temporary/duration-gated" suppression logic that guards blindsight/truesight (lines 778-780) is explicitly commented as having been written with Stonecunning's own Tremorsense in mind as the case that suppression protects against, not as something meant to ever match it. (2) `usesFormula` (lines 438-457) only recognizes a literal ability-modifier phrase, a number-word immediately before "times" ("three times"), or bare "once"/"twice" — "a number of times equal to your Proficiency Bonus" matches none of the three, so the uses count is silently dropped even though `@prof` is a resolvable roll-data term the module already knows how to emit elsewhere (e.g. `parseDcFormula`, the flat-mechanic `profRe` scanner). (3) `parseActivation` (line 322) does correctly classify this as `type: "bonus"` via `BONUS_ACTION_PHRASE_RE`, but that value is only ever attached to an activity/effect actually built from a save/damage/heal/cast/toggle hint — since none of those fire here, the detected activation type has nothing to attach to and is discarded. Net result: zero effects, zero activities, even after issues 016/017/019.
- **Actual (compendium data):** `effects: []`, `activities: {}`. Matches expectation.
- **Gap / verdict:** Confirmed "no detector covers this" case, exactly as anticipated. Two independent, generalizable gaps: (a) Tremorsense is missing from the blindsight/truesight-style sense list (even though a real activity-gated grant needs a different shape than that list's permanent-effect assumption — it would need to become a real Activity that applies a temporary effect, not a static change); (b) "a number of times equal to your Proficiency Bonus" as an uses-count phrasing is not recognized by `usesFormula` alongside the existing ability-modifier/number-word/once-twice forms. Neither is covered by issues 001-019 — both are new findings.

### Size
- **Prose:** "You are Medium (about 4–5 feet tall)."
- **Expected (current code):** Nothing from `scanSegmentText` — there is no "you are <Size>" prose detector anywhere in scraper.mjs; Size is handled structurally, not from prose. The actual Size mechanic is built by `buildSizeAdvancement` (scripts/ddb-scraper.mjs:248-265) reading `raceDef.sizeId` (not this trait's text) and is attached only to the **race item's** `system.advancement`, via `assembleRaceItem` (ddb-scraper.mjs:324-362, spread in at line 340). So the Size trait item itself is expected to always be an inert flavor-text stub; that's by design, not a bug.
- **Actual (compendium data):** `effects: []`, `advancement: {}`. Matches expectation for the trait item.
- **Gap / verdict:** No gap on the trait item itself. But since Dwarf has no race item at all (finding #1), the Size advancement that `buildSizeAdvancement` would have produced never landed anywhere in this pack — Dwarf currently has no Medium-size data recorded anywhere in the compendium, trait or race item.

### Darkvision
- **Prose:** "You have Darkvision with a range of 120 feet."
- **Expected (current code):** Matches. `darkvisionMatch`'s first alternative (scripts/scraper.mjs:752-756) — `darkvision(?:\s+(?:out to|with|to|of|radius of)\s+(?:a range of\s+)?)?\s*(\d+)\s*feet` — matches "Darkvision with a range of 120 feet" directly, producing `{key: "system.attributes.senses.darkvision", mode: 4 (UPGRADE), value: "120"}`.
- **Actual (compendium data):** `effects: []`.
- **Gap / verdict:** Real gap, but purely a staleness artifact — re-importing today would correctly populate this effect. No code fix needed.

### Ability Score Increases
- **Prose:** "When determining your character's ability scores, increase one score by 2 and a different one by 1, or increase three scores by 1. None of these increases can raise a score above 20."
- **Expected (current code):** Nothing is built, and this is a real code gap, not staleness. `guessAbilityScoreImprovement` (scripts/scraper.mjs:881-910) anchors on the sentence regex at line 884: `/Increase\s+(?:your|one ability score of your choice|two ability scores of your choice)[^.]*\./i`. This requires the word immediately after "Increase" to be "your", "one ability score of your choice", or "two ability scores of your choice" — the feat/half-feat 2024 boilerplate. The species-level 2024 PHB phrasing used here ("increase one **score** by 2 and a different one by 1, or increase three **scores** by 1") never contains the phrase "ability score of your choice" at all, so the sentence match fails outright and the function returns `null` — no ASI advancement is ever generated for this trait, on any species, under current code. Confirmed via grep: no reference to this species-ASI phrasing exists anywhere in scraper.mjs, ddb-scraper.mjs, or issues 001-019 — this is a genuinely new, previously undocumented gap.
- **Actual (compendium data):** `advancement: {}`. Consistent with the code gap (would still be empty even on a fresh, non-stale import).
- **Gap / verdict:** **New finding, not staleness.** Every core 2024 species' "Ability Score Increases" trait uses this same fixed PHB boilerplate, so this silently drops the entire ASI grant for every species import done via this pipeline, not just Dwarf's. Worth its own issue: extend `guessAbilityScoreImprovement`'s sentence regex (or add a second species-specific pattern) to recognize "increase one score by 2 and a different one by 1, or increase three scores by 1" and map it to the same `{points: 2, cap: 2, locked: []}` `AbilityScoreImprovement` configuration the "two ability scores of your choice by 1" feat phrasing already maps to (line 899) — the mechanic is identical, only the wording differs.

### Dwarven Toughness
- **Prose:** "Your Hit Point maximum increases by 1, and it increases by 1 again whenever you gain a level."
- **Expected (current code):** Matches, and by design — this is the exact confirmed phrasing `hpPerLevelMatch` (scripts/scraper.mjs:569-570) was written against: `/hit point maximum increases by (\d+)\b[^.]*\bwhenever you gain a level\b/i`, produced from issue 012. It matches this text cleanly (no intervening period between "by 1" and "whenever you gain a level"), producing `{key: "system.attributes.hp.bonuses.level", mode: 2 (ADD), value: "1"}`.
- **Actual (compendium data):** `effects: []`.
- **Gap / verdict:** Staleness only — the "known hard case" flagged in the audit brief has already been fixed (issue 012, merged in commit `5e375a9`/`e160cc0`) and is explicitly comment-referenced by name as having been written for this exact trait. A re-import today would populate this correctly.

### Speed
- **Prose:** "Your speed is 30 ft."
- **Expected (current code):** Nothing is built from this trait's own text, for two independent reasons. First, none of `scanSegmentText`'s three speed regexes (scripts/scraper.mjs:712, 724, 736) match a flat "your speed is N" statement — they only recognize delta phrasing ("speed increases by/to N feet") or an absolute directional grant ("you have a walking speed of N feet"); a flat non-directional "is" statement matches none of the three shapes. Second, even setting phrasing aside, every one of those regexes (and `ddb-scraper.mjs`'s own `ABSOLUTE_SPEED_GRANT`/`WALKING_SPEED_INCREASES_TO` at lines 273-274, used by `mergeTraitDerivedMovement` for the race item's movement) hardcodes the unit word `feet`; this trait's actual text abbreviates to `ft.`, which none of them would match even if the phrasing were otherwise compatible.
- **Actual (compendium data):** `effects: []`.
- **Gap / verdict:** Not a meaningful gap in practice — real movement speed for the race item is meant to come structurally from `raceDef.weightSpeeds.normal` in `assembleRaceItem` (ddb-scraper.mjs:326), independent of this trait's prose; `mergeTraitDerivedMovement` exists only to backfill species whose weightSpeeds is missing a direction a trait states explicitly (e.g. Wood Elf's Fleet of Foot). A flat "is 30 ft." restating the already-structured base speed isn't a case that pipeline needs to catch. The bigger issue is that Dwarf's actual speed data depends entirely on the (currently missing) race item — see Species-level notes.

### Creature Type
- **Prose:** "You are a Humanoid."
- **Expected (current code):** Nothing — there is no "you are a &lt;type&gt;" creature-type detector anywhere in scraper.mjs (confirmed via grep). This is expected/reasonable: `assembleRaceItem` (ddb-scraper.mjs:342-346) already hardcodes `type: {value: "humanoid", ...}` on the race item directly (5e rule: playable species are Humanoid unless stated otherwise, per the code's own comment), so this trait's text is redundant flavor DDB includes and was never meant to be scanned.
- **Actual (compendium data):** `effects: []`.
- **Gap / verdict:** No real gap — by-design inert stub, matches expectation exactly.

## Species-level notes

- **Race item absence confirmed for Dwarf** (`raceItemExists: false`), consistent with the pack-wide finding across all 9 core PHB species. Static review of `assembleRaceItem`/`buildSizeAdvancement`/`mergeTraitDerivedMovement` (ddb-scraper.mjs) does not reveal an obvious throw path for normal input shapes — `importDdbRace` (importer.mjs:929-963) wraps trait creation and race-item creation in one try/catch, so an exception during the *final* `createItemFromData(assembleRaceItem(...), ...)` call would explain exactly this pattern (traits persisted because each is `await`ed and committed individually before the race item step runs; a later throw is caught and only reported via `report.failed`, never rolled back). None of the per-trait prose gaps found above (Speed's "ft." vs "feet", Ability Score Increases' unmatched phrasing) can throw — they just silently return null/no-op — so they are not candidates for the actual crash. Root-causing the real exception needs the console/log output from the actual 2026-08-24 import run, which isn't available for static review; this is a good candidate for a dedicated runtime-debugging follow-up rather than something resolvable by re-reading the source.
- **Downstream effect of the missing race item:** because `buildSizeAdvancement` and the movement/speed data both attach only to the race item (never to any trait), Dwarf currently has **no** Size advancement and **no** movement/speed data anywhere in the compendium — not because those detectors are broken, but because the one item they'd attach to was never persisted.
- **Cross-species implication:** the Ability Score Increases gap (species-level PHB boilerplate not matching the feat-level ASI regex) is structural and will reproduce identically for Human, Elf, Halfling, Gnome, Dragonborn, Orc, Tiefling, and Goliath — none of the core species' ASI grants would import correctly even on a fresh, non-stale run today.
