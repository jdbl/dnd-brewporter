# Species Audit: Tiefling

## Summary

No `race`-type Item exists for Tiefling (`raceItemExists: false`), consistent with the cross-species finding that all 9 core PHB 2024 species failed to get a race item while 7 non-core species succeeded. All 12 trait items have completely empty `effects`/`activities`/`advancement` — the raw placeholder shape `buildRaceTraitItemData` initializes (`scripts/ddb-scraper.mjs:182-209`), not "scanned and found nothing." Unlike some other species, Tiefling's emptiness is **not fully explained by import staleness**: several traits (Darkvision, Hellish Resistance, Infernal Legacy's Hellish Rebuke/Darkness) would in fact populate correctly on a fresh reimport against the current working tree, but several others would **still come back empty or actively wrong** even under current code — most importantly a **cantrip-name-capture bug** that silently drops every "you know the X cantrip" grant (Otherworldly Presence, Infernal Legacy's Thaumaturgy, and all three Fiendish Legacy cantrips), and a **table-flattening bug** that would cause "Fiendish Legacy" to grant all three mutually-exclusive legacies' damage resistances simultaneously if it fired at all. The Tiefling trait set also contains a genuine **duplicate-import artifact**: 12 items for what should be ~9-10 distinct traits, including two differently-worded "Darkvision" entries and two differently-worded Ability-Score-Increase traits, strongly suggesting a legacy/2014-or-MPMM trait set and the 2024 PHB trait set were both pulled into the same species' `racialTraits` array and imported side by side.

Note on code version: this audit evaluates the **working tree as checked out** (branch `ddb-species-feats-import`, HEAD `e160cc0` plus uncommitted modifications to `scripts/scraper.mjs`/`effects-builder.mjs`/`importer.mjs`). Those uncommitted changes already implement issues 016, 017, and 019 in full (confirmed via `git diff` — `parseDcFormula`, `parseActivation`/`parseRangeAndTarget`, and the relaxed `have|has|know|knows|learn|learns` cast-verb regex are all present on disk) and issue 018 (feat-only, not relevant to species import). Since Foundry runs whatever is on disk, not the last commit, "current code" below means this working-tree state.

## Traits

### Infernal Legacy
- **Prose:** "You know the thaumaturgy cantrip. When you reach 3rd level, you can cast the hellish rebuke spell as a 2nd-level spell once with this trait and regain the ability to do so when you finish a long rest. When you reach 5th level, you can cast the darkness spell once with this trait and regain the ability to do so when you finish a long rest. Charisma is your spellcasting ability for these spells."
- **Expected (current code):** Partial detection. The relaxed cast-verb regex (`scripts/scraper.mjs:422`, issue 019) scans for `(?:casts?(?:ing)?|have|has|know|knows|learn|learns)\s+(?:the\s+)?(...)(?:spell)?`. "cast the hellish rebuke spell" and "cast the darkness spell" both match cleanly (capture stops before the literal trailing "spell"), and both "Hellish Rebuke" and "Darkness" are real compendium spell names, so `guessQueueEntries` (`scripts/effects-builder.mjs:876-893`) builds two `cast` Activities. Each gets `usesMax: "1"` / `recovery: [{period: "lr"}]` from `scanSegmentText`'s once/long-rest detection (`scripts/scraper.mjs:432-457`). However, "know **the thaumaturgy cantrip**" does **not** match: the capture group `((?:(?!spell\b)[A-Za-z][a-zA-Z']*\s*){1,4})` excludes the literal word "spell" from being swallowed, but has no equivalent exclusion for "cantrip" — so it greedily captures "thaumaturgy cantrip" as one two-word candidate, which fails the exact-match lookup against the spell index (the real spell name is just "Thaumaturgy"). This is a genuine, previously-undocumented gap in the cast-detection regex, not covered by issue 019 (which only broadened the verb list, not the cantrip/spell trailing-word handling). Separately, "Charisma is your spellcasting ability for these spells" is never parsed by anything — `buildActivityData`'s `cast` branch (`scripts/effects-builder.mjs:592-604`) always sets `spell: { ability: "", ... }` regardless of what the prose says, so even the two correctly-detected spells would cast using the actor's default spellcasting ability, not Charisma.
- **Actual (compendium data):** Empty.
- **Gap / verdict:** Mixed. The Hellish Rebuke/Darkness misses are pure staleness (would be fixed by reimport). The Thaumaturgy miss (cantrip-capture bug) and the spellcasting-ability-override miss are real, current gaps that a reimport would **not** fix.

### Size
- **Prose:** "You are Medium (about 4–7 feet tall) or Small (about 3–4 feet tall), chosen when you select this species."
- **Expected (current code):** Nothing from the trait item itself — no `scanSegmentText` pattern matches this phrasing. The real mechanic belongs on the *race item* via `buildSizeAdvancement` (`scripts/ddb-scraper.mjs:248-265`), which reads `raceDef.sizeId`, not this trait's prose. `SIZE_ID_TO_DND5E`'s `10 → ["sm","med"]` entry is exactly the shape Tiefling's own "Medium or Small, chosen when you select this species" text describes, so if the race item existed and `sizeId` were 10, this would resolve correctly.
- **Actual (compendium data):** Empty — expected, non-mechanical trait text.
- **Gap / verdict:** No gap on the trait item. The real mechanic never landed anywhere because the race item was never created (finding #1).

### Darkvision (two entries, different wording)
- **Prose (2024 boilerplate, `Xx7qUalAQJWp1m9P`):** "Thanks to your infernal heritage, you have superior vision in dark and dim conditions. You can see in dim light within 60 feet of you as if it were bright light, and in darkness as if it were dim light. You can't discern color in darkness, only shades of gray."
- **Prose (short/legacy form, `gNLe8MU4Nlvn9DpA`):** "You have Darkvision with a range of 60 feet."
- **Expected (current code):** Both match cleanly, via two different alternatives of the same regex chain (`scripts/scraper.mjs:752-758`). The 2024 boilerplate matches the third alternative, `\bsee in dim light within\s+(\d+)\s*feet\s+of you as if it were bright light\b`. The short form matches the first alternative directly (`darkvision...with...(\d+)\s*feet`). Each independently produces the identical ActiveEffect change `{key: "system.attributes.senses.darkvision", mode: 4 (UPGRADE), value: "60"}`.
- **Actual (compendium data):** Both empty.
- **Gap / verdict:** Pure staleness — both would populate correctly on reimport, each producing its own (functionally redundant) 60-ft darkvision effect. The real issue with this pair isn't detection, it's that there are **two Darkvision items at all** — see Species-level notes.

### Otherworldly Presence
- **Prose:** "You know the Thaumaturgy cantrip. When you cast it with this trait, the spell uses the same spellcasting ability you use for your Fiendish Legacy Trait."
- **Expected (current code):** Nothing. This is the clearest illustration of the cantrip-capture bug described under Infernal Legacy: "know the Thaumaturgy cantrip" captures "Thaumaturgy cantrip" as the candidate name, which fails the exact spell-name lookup, so **no cast Activity is built at all** for what is explicitly called out in this audit's brief as "an innate Thaumaturgy-like cantrip usable at will." The second sentence ("cast it with this trait...") doesn't help either — "cast it" captures a run of following filler words ("it with this trait"), none of which resolve to a real spell name.
- **Actual (compendium data):** Empty.
- **Gap / verdict:** Genuine current-code gap, not staleness. Fixing the cantrip-capture bug in the shared cast-verb regex (`scripts/scraper.mjs:422`) — e.g. adding `cantrip` alongside `spell` in the trailing optional literal, and excluding it from the capture group the same way `spell` is excluded — would fix this trait (and Infernal Legacy's and Fiendish Legacy's cantrip misses below) in one place. Not covered by issue 019.

### Ability Score Increase (singular — legacy/MPMM-style)
- **Prose:** "Your Intelligence score increases by 1, and your Charisma score increases by 2."
- **Expected (current code):** No ASI advancement. `guessAbilityScoreImprovement`'s sentence-extraction regex (`scripts/scraper.mjs:884`) requires the literal word "Increase" to lead, followed immediately by "your"/"one ability score of your choice"/"two ability scores of your choice." This text is phrased the opposite way around ("Your Intelligence score **increases** by 1..."), so the substring the regex needs never occurs anywhere in the sentence, and `guessAbilityScoreAdvancement` returns `null`.
- **Actual (compendium data):** Empty.
- **Gap / verdict:** Genuine current-code gap. This is the pre-2024/MPMM fixed-ability-score phrasing family ("X score increases by N, and Y score increases by M") used by every 2014 PHB race — entirely unsupported by `guessAbilityScoreImprovement`, which was written and verified only against feat/Epic-Boon boilerplate. Not covered by issue 009 (which only wires the existing detector into `buildAutoMechanics`, without extending its phrasing coverage).

### Fiendish Legacy Spells
- **Prose:** "When you choose your Fiendish Legacy, and at character levels 3 and 5, you learn a spell as shown on the table. You always have that spell prepared. You can cast it once without a spell slot, and you regain the ability to cast it in that way when you finish a Long Rest. You can also cast the spell using any spell slots you have of the appropriate level. Intelligence, Wisdom, or Charisma is your spellcasting ability for the spells you cast with this trait (choose the ability when you select the legacy)."
- **Expected (current code):** Nothing, and appropriately so at this level: this trait's own text never names a concrete spell (the actual spell names live on the "Fiendish Legacy" trait's table, a separate item) — every "learn a spell"/"have that spell"/"cast the spell" phrase here is a generic placeholder reference, so the cast-verb regex's captured candidates ("a", "that", "the", etc.) correctly fail the exact spell-name lookup and nothing false-positives.
- **Actual (compendium data):** Empty — matches expectation exactly.
- **Gap / verdict:** No gap for *this* trait's own text. The real gap is structural and is discussed in depth under Species-level notes: there is no advancement type anywhere in the codebase capable of modeling a "learn a table-driven spell at level 1/3/5, tied to a legacy chosen elsewhere" progression, even in principle.

### Ability Score Increases (plural — 2024 PHB phrasing)
- **Prose:** "When determining your character's ability scores, increase one score by 2 and a different one by 1, or increase three scores by 1. None of these increases can raise a score above 20."
- **Expected (current code):** No ASI advancement — same root cause as "Ability Score Increase" above but a different phrasing family. `guessAbilityScoreImprovement`'s regex requires "Increase" to be immediately followed by "your," "one ability score of your choice," or "two ability scores of your choice." This species-level 2024 phrasing says "increase **one score** by 2... or increase **three scores** by 1" — structurally the same rule as the feat-level "one ability score of your choice by 2, or two ability scores of your choice by 1," but worded differently enough that none of the three required substrings appear, so the whole detector misses it.
- **Actual (compendium data):** Empty.
- **Gap / verdict:** Genuine current-code gap, **not staleness**, and not Tiefling-specific — this is the exact same 2024 PHB species-level ASI boilerplate every 2024 core species uses (independently confirmed against the Human audit in this same `audits/` directory, which hits the identical regex-anchor mismatch). This means literally no 2024 species gets an Ability Score Increase advancement today regardless of import freshness — arguably the single highest-value fix among everything found across this audit pass, since it silently affects every species, not just edge cases.

### Hellish Resistance
- **Prose:** "You have resistance to fire damage."
- **Expected (current code):** Matches cleanly. `traitRe` (`scripts/scraper.mjs:582-590`) matches "resistance to fire damage," "fire" is in `DAMAGE_TYPE_WORDS`, producing one effect hint `{key: "system.traits.dr.value", mode: 2 (ADD), value: "fire"}`. No other detector fires on this text (no dice, no saves, no conditions).
- **Actual (compendium data):** Empty.
- **Gap / verdict:** Pure staleness — this is the clean contrast case the audit brief called out. Current code handles single, plain resistance grants correctly with no gaps; a reimport would populate this trait's `effects` correctly.

### Fiendish Legacy
- **Prose:** "You are the recipient of a legacy that grants you supernatural abilities. Choose a legacy from the Fiendish Legacies table. You gain the level 1 benefit of the chosen legacy. When you reach character levels 3 and 5, you learn a higher-level spell, as shown on the table. You always have that spell prepared... Intelligence, Wisdom, or Charisma is your spellcasting ability..." followed by a `<table>` listing three legacies (Abyssal/Chthonic/Infernal), each with a level-1 benefit (a damage resistance + a cantrip) and level-3/level-5 spell names.
- **Expected (current code):** This is the most consequential finding in the audit. `guessFeatureMechanics` (`scripts/scraper.mjs:833-865`) segments a trait's HTML by top-level block elements, starting a new segment only when a block opens with a bold label. The `<table>` here has no leading bold tag, so it is **not** split into its own segment or into per-row/per-legacy segments — it's folded into the same single segment as the two preceding `<p>` blocks, and `el.textContent` flattens the entire table (caption, headers, all three rows) into one linear text blob (`scripts/scraper.mjs:859`). Running `traitRe` against that blob finds **all three** "Resistance to `<Type>` damage" phrases — Poison, Necrotic, and Fire — and builds a single ActiveEffect on the "Fiendish Legacy" item granting **all three resistances simultaneously**, even though the table describes three *mutually exclusive* player choices. The three cantrips (Poison Spray/Chill Touch/Fire Bolt) are separately missed by the same cantrip-capture bug described above, and the level-3/5 spell names (Ray of Sickness, Hold Person, False Life, Ray of Enfeeblement, Hellish Rebuke, Darkness) sit as bare table-cell text with no adjacent "cast/learn/have" verb at all once whitespace-collapsed, so the cast-verb regex has no anchor to match them regardless of the cantrip bug — they are structurally invisible to this detector, full stop.
- **Actual (compendium data):** Empty.
- **Gap / verdict:** Staleness is not the interesting story here — even a fresh reimport against current code would produce an **actively wrong** result (three simultaneous resistances) rather than nothing, once the current empty state (which happens to look "safe") is compared against what the pipeline would really build. This is a structural gap distinct from any single regex fix: `guessFeatureMechanics`/`scanSegmentText` has no concept of "this table encodes N mutually exclusive options" — that's a fundamentally different problem from a missed keyword. `buildAdvancement`'s own table-to-choice parsing (`scripts/scraper.mjs:1404` onward) exists but is class-feature-table-specific and is never invoked from the race-trait auto-mechanics path at all. Not covered by any of issues 001-019; recommend filing as its own issue given the correctness risk (silently over-granting resistances is worse than granting nothing).

### Speed
- **Prose:** "You have a Speed of 30 feet."
- **Expected (current code):** No effect. All three speed regexes in `scanSegmentText` (`scripts/scraper.mjs:712,724,736`) require an explicit movement-type word ("walking," "climbing," "swimming," "flying," or "burrowing") directly before "speed" — none require it, but this bare/default phrasing has none of those words at all ("a Speed of 30 feet," not "a walking Speed of..."). This is the plain, undecorated base-speed statement essentially every species trait set includes, and it is completely unmatched by any current regex.
- **Actual (compendium data):** Empty.
- **Gap / verdict:** Real detector gap on the trait item, but low practical impact for Tiefling specifically: the race item's own `system.movement.walk` is meant to come from structured `raceDef.weightSpeeds?.normal` data via `assembleRaceItem` (`scripts/ddb-scraper.mjs:326`), not from this trait's prose — so if the race item existed, Tiefling would still end up with the correct 30-ft walking speed regardless of this trait-text miss. Because the race item doesn't exist (finding #1), Tiefling's imported character currently has **no walking speed set at all**, from either path.

### Creature Type
- **Prose:** "You are a Humanoid."
- **Expected (current code):** No effect — there is no creature-type detector anywhere in `scanSegmentText`. `assembleRaceItem` (`scripts/ddb-scraper.mjs:342-346`) hardcodes `system.type.value: "humanoid"` on the race item unconditionally, independent of this trait's own prose, per its own comment that "playable species are Humanoid unless stated otherwise" in both rulesets.
- **Actual (compendium data):** Empty.
- **Gap / verdict:** No gap on the trait item — inherently non-mechanical flavor text; the real mechanic (which happens to already be correct for Tiefling) lives on the missing race item.

## Species-level notes

**Missing race item (finding #1, confirmed for Tiefling).** `raceItemExists: false`. Nothing in `importDdbRace` (`scripts/importer.mjs:929-963`) special-cases core vs. non-core species by name — the loop creates all 12 trait items successfully (all 12 appear in the compendium with real `_id`s), then calls `buildSizeAdvancement`, `mergeTraitDerivedMovement`, and finally `createItemFromData(assembleRaceItem(...))` inside the same try/catch as the trait loop. Since every trait item was already created before that final step runs, whatever failed did so specifically in the size/movement/race-item-assembly tail of the function, and the whole thing is swallowed into `report.failed` rather than surfacing loudly. This audit's available data (trait JSON only, no import report) can't pin down which exact statement threw; that would need the raw `raceDef` payload or the actual `report.failed` entry for Tiefling.

**Duplicate-trait artifact — two overlapping trait generations, not two copies of one trait.** Tiefling has 12 trait items for what 2024 PHB Tiefling alone would need (Size, Ability Score Increases, Creature Type, Speed, Darkvision, Otherworldly Presence, Fiendish Legacy, Fiendish Legacy Spells, Hellish Resistance — 9 traits). The 3 extras are **Infernal Legacy**, **Ability Score Increase** (singular), and a second **Darkvision** — and critically, the "duplicates" are not identical copies: Infernal Legacy vs. Fiendish Legacy have different names, different identifiers, and completely different mechanical text (Infernal Legacy is the fixed pre-2024 Thaumaturgy/Hellish-Rebuke-at-3/Darkness-at-5 progression; Fiendish Legacy is the 2024 three-way legacy-choice table). Likewise the two Ability-Score-Increase traits encode genuinely different rules (fixed +1 Int/+2 Cha vs. the flexible 2024 point-buy), and the two Darkvision traits use different wording for the same 60-ft grant. This pattern — same conceptual trait, two different rules-generation's wording, both landing in one species' `racialTraits` array — points to a data-fetch issue upstream of anything in `scraper.mjs`/`ddb-scraper.mjs`/`effects-builder.mjs`/`importer.mjs`: `usableRacialTraits` (`scripts/ddb-scraper.mjs:165-169`) filters D&D Beyond's trait list only on `hideInSheet`, with no ruleset/legacy filtering at all, so if D&D Beyond's underlying Tiefling race entity actually bundles a legacy/MPMM-era trait set alongside its 2024 PHB trait set (plausible if this "Tiefling" entity is a base-race-plus-variant construction on D&D Beyond's side), every trait from both generations comes through as "usable" and gets imported side by side. This is currently mostly inert (most of the legacy-phrased traits aren't detected by the current mechanics scanner anyway — see Ability Score Increase above), but it is a real double-import risk once any of those phrasing gaps get fixed, and it's worth investigating the raceDef-fetch layer (outside the four files in scope for this audit) to confirm whether this is a single overloaded entity or an actual duplicate API call.

**Legacy-choice spellcasting progression has no modeling path at all, even in principle.** The 2024 Tiefling's core identity mechanic — choose one of three legacies at level 1, then learn a scaling, legacy-specific spell at levels 3 and 5, using a player-chosen spellcasting ability — has zero support anywhere in this codebase:
- No advancement type exists for "grant a specific item/spell at a specific character level conditioned on an earlier choice" outside of `buildRaceAdvancement`'s flat `ItemGrant` (`scripts/ddb-scraper.mjs:218-232`), which grants a fixed set of items at a fixed level with no branching.
- `guessFeatureMechanics`/`scanSegmentText` operate purely on flattened block text with no table-structure awareness (see the Fiendish Legacy write-up above) — the only table-aware advancement builder in the codebase, `buildAdvancement` (`scripts/scraper.mjs:1404` onward), is wired exclusively into class-feature import, not race-trait import.
- Even the achievable subset — recording which of Intelligence/Wisdom/Charisma the player chose as their innate spellcasting ability — has no destination field: `buildActivityData`'s `cast` type hardcodes `spell.ability: ""` (`scripts/effects-builder.mjs:602`), so nothing produced by this pipeline, today or with any of the phrasing fixes above applied, would ever carry that override through to an actual Activity.

Building real support for this would be a materially larger effort than any single regex fix — closer to a new "table-driven leveled choice" advancement type — and is worth flagging as its own, larger design question rather than an incremental issue.

**New gaps found, not covered by issues 001-019 (worth filing):**
1. Cast-verb regex (`scripts/scraper.mjs:422`) captures a trailing "cantrip" as part of the spell-name candidate instead of excluding/consuming it the way it already does "spell" — silently drops every "you know the X cantrip" grant (hits Otherworldly Presence, Infernal Legacy's Thaumaturgy, and all three Fiendish Legacy table cantrips for this species alone).
2. `guessAbilityScoreImprovement` doesn't recognize the pre-2024/MPMM fixed-ability-score phrasing ("X score increases by N, and Y score increases by M") at all.
3. `guessAbilityScoreImprovement` also doesn't recognize the 2024 **species-level** ASI phrasing ("increase one score by 2 and a different one by 1, or increase three scores by 1") — distinct regex-anchor mismatch from #2, and (per the Human audit in this same directory) confirmed to affect every 2024 core species identically, making this the highest-value fix found across the audit.
4. `guessFeatureMechanics` has no table/choice-structure awareness — a `<table>` describing N mutually exclusive options gets flattened into one text blob and scanned as if every row applied simultaneously, which for Fiendish Legacy would actively over-grant three resistances at once rather than safely detecting nothing.
5. No spellcasting-ability override (e.g. "Charisma is your spellcasting ability for these spells") is ever captured or wired into a built `cast` Activity's `spell.ability` field — affects Infernal Legacy, Otherworldly Presence, and Fiendish Legacy/Fiendish Legacy Spells simultaneously.
6. Possible duplicate-trait-generation import (legacy/MPMM-era traits and 2024 PHB traits both present in one species' trait list) upstream of the four in-scope files — worth checking whatever builds `raceDef.racialTraits` before assuming this is purely a scraper.mjs/effects-builder.mjs problem.
