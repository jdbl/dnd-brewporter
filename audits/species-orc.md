# Species Audit: Orc

## Summary

No `race`-type item exists for Orc in the compendium (`raceItemExists: false`) — only the 7 trait `feat` items exist, consistent with the pack-wide finding across all 9 core PHB 2024 species. Every trait's `effects`/`activities`/`advancement` are empty, and for most traits that's a pure staleness artifact (Darkvision would populate correctly on re-import today). But two traits expose real, still-open gaps in the current (working-tree) pipeline: **Ability Score Increases** uses the PHB-2024 species boilerplate that the ASI regex doesn't recognize at all (a cross-species gap, not new to Orc), and **Adrenaline Rush** — the 2024 replacement for Relentless Endurance — has its "gain temp HP equal to Proficiency Bonus" half detected, but its "usable a number of times equal to your Proficiency Bonus" limited-use clause is silently dropped, so even a fresh re-import would build a heal Activity with no uses/recovery data at all. The most striking species-level anomaly is that **both** Adrenaline Rush (2024) and Relentless Endurance (2014, the trait it replaced) are present in this same import — a data-provenance issue upstream of any prose-parsing gap.

Note on repo state: `scripts/scraper.mjs`, `scripts/effects-builder.mjs`, and `scripts/importer.mjs` have uncommitted working-tree changes that already implement issues 016 (DC formula / uses-recovery wiring), 017 (activation/range/target/toggle linking), and 019 (relaxed always-prepared spell verbs) — not yet committed (`git log` HEAD is `e160cc0`), but this is what's actually on disk and what a live import would run today. Issue 018 (Magic Initiate class narrowing) is unrelated to species entirely. All findings below evaluate "current code" as this on-disk state, not the last commit.

## Traits

### Darkvision
- **Prose:** "You have Darkvision with a range of 120 feet."
- **Expected (current code):** Matches directly. `darkvisionMatch`'s first alternative (scripts/scraper.mjs:752-756) — `darkvision(?:\s+(?:out to|with|to|of|radius of)\s+(?:a range of\s+)?)?\s*(\d+)\s*feet` — matches "Darkvision with a range of 120 feet", producing an ActiveEffect change `{key: "system.attributes.senses.darkvision", mode: 4 (UPGRADE), value: "120"}`. `guessQueueEntries` (effects-builder.mjs:900-913) wraps this into a permanent, `transfer: true` Effect named "Darkvision" (falls back to `featureName` since the segment has no bold label).
- **Actual (compendium data):** `effects: []`. Confirms the empty-pack finding.
- **Gap / verdict:** Staleness only — a re-import today would populate this effect correctly. No code fix needed.

### Speed
- **Prose:** "Your Speed is 30 feet."
- **Expected (current code):** Nothing is built from this trait's own text. None of `scanSegmentText`'s three speed regexes (scripts/scraper.mjs:712, 724, 736) recognize a flat "your Speed is N feet" statement — they only match delta phrasing ("speed increases by/to N feet") or an absolute directional grant ("you have a walking speed of N feet"), and a bare non-directional "is" statement matches none of the three shapes.
- **Actual (compendium data):** `effects: []`. Matches expectation.
- **Gap / verdict:** Not a meaningful gap in practice. The real walking-speed value is meant to come structurally from `raceDef.weightSpeeds.normal` via `assembleRaceItem` (ddb-scraper.mjs:324-355), independent of this trait's prose — confirmed 30ft is standard Orc speed and would be set correctly on the race item if one existed. Since no race item was persisted for this species (see Species-level notes), the actual mechanical speed value currently lives nowhere in this compendium, trait or race item — but that is a downstream consequence of the missing race item, not a prose-detection failure on this trait.

### Size
- **Prose:** "Your Size is Medium (about 6–7 feet tall)."
- **Expected (current code):** Nothing from `scanSegmentText` — there is no "your Size is X" prose detector anywhere in scraper.mjs. Size is handled structurally: `buildSizeAdvancement` (ddb-scraper.mjs:248-265) reads `raceDef.sizeId` (not this trait's text) and attaches a `Size` advancement entry only to the **race item's** `system.advancement` (ddb-scraper.mjs:340). The Size trait item itself is an inert flavor-text stub by design.
- **Actual (compendium data):** `effects: []`, `advancement: {}`. Matches expectation for the trait item.
- **Gap / verdict:** No gap on the trait item itself. Because Orc has no race item (finding #1), the Medium-size Size advancement `buildSizeAdvancement` would have produced never landed anywhere in this pack.

### Adrenaline Rush
- **Prose:** "You can take the Dash action as a Bonus Action. When you do so, you gain a number of Temporary Hit Points equal to your Proficiency Bonus. You can use this trait a number of times equal to your Proficiency Bonus, and you regain all expended uses when you finish a Short or Long Rest."
- **Expected (current code):** Both `<p>` blocks have no leading bold label, so they merge into one segment (scraper.mjs:839-848) and are scanned together.
  - **Activation:** `BONUS_ACTION_PHRASE_RE` (scraper.mjs:312) matches "as a Bonus Action" → `activation.type = "bonus"`. `TRIGGER_CLAUSE_RE` (line 320) is anchored to the very start of the segment and the text opens with "You can take…", not a When/Whenever/If clause, so no `activation.condition` is captured — reasonable, since the actual trigger *is* the bonus action itself.
  - **Temp HP:** `profRe` (scraper.mjs:533-543) matches "…Temporary Hit Points equal to your Proficiency Bonus" — the 60-char backward window contains "temporary hit points", so it correctly classifies as `{formula: "@prof", kind: "heal", type: "temphp"}`. This becomes a `heal`-type Activity via `guessQueueEntries` (effects-builder.mjs:872-874) with `activationType: "bonus"`.
  - **Uses count — gap:** "a number of times equal to your Proficiency Bonus" is never captured as `usesFormula`. The `usesFormula` detector (scraper.mjs:438-457) only recognizes an ability-modifier phrase, an explicit number-word immediately before "times" ("three times"), or a bare "once"/"twice" — it has no path from "proficiency bonus" to a `@prof` uses count, even though `@prof` is a roll-data term this module already emits elsewhere (`parseDcFormula`, the flat-mechanic `profRe` scanner itself, two lines above). Result: `usesFormula` stays `null`, so `buildActivityData`'s `uses.max` (effects-builder.mjs:570) is built from an empty string. Because `uses: form.usesMax ? [...] : []`, the recovery array is **also** forced empty regardless of what recovery period was detected — the whole limited-use shape of this trait is silently discarded.
  - **Recovery period — second, independent bug:** even if `usesMax` were non-empty, the recovery period would be wrong. `recoveryPeriod` (scraper.mjs:432-436) is computed by finding the first literal-substring index of "short rest" vs. "long rest". The text reads "…finish a Short or Long Rest" — "Short" is followed by "or Long Rest", not "Rest", so the literal substring "short rest" never appears and `srIdx = -1`; only "Long Rest" (the tail of "or Long Rest") matches, so `recoveryPeriod` resolves to `"lr"` — long-rest-only — when the actual trait recovers on *either* a short or long rest (which dnd5e's own convention represents as period `"sr"`, since a long rest also satisfies short-rest recovery). This bug is currently masked by the uses-count gap above (recovery is discarded either way), but would misfire the moment that gap is fixed.
  - Neither gap is addressed by issues 001-019, nor did issue 016 ("uses/recovery wiring") extend the uses-count *value* parser itself — it only wired the existing `usesFormula`/`recoveryPeriod` fields through to every activity type, which doesn't help when the value never gets computed in the first place.
- **Actual (compendium data):** `effects: []`, `activities: {}`. Consistent with the code gaps above — even a fresh, non-stale re-import today would still produce an incomplete result (a temp-HP heal Activity with a correct bonus-action trigger, but no uses cap and no recovery), not the fully-correct trait.
- **Gap / verdict:** Partial detection, two new confirmed gaps: (1) no "N times equal to your Proficiency Bonus" → `@prof` uses-count mapping exists anywhere in `usesFormula`; (2) the short/long-rest string-search in `recoveryPeriod` doesn't handle the shared "a Short or Long Rest" conjunction and would misclassify it as long-rest-only. Worth a follow-up issue extending `usesFormula` with an ability-modifier-style `@prof`-count pattern (parallel to the existing `@abilities.X.mod` case) and fixing the short/long-rest substring search to recognize a shared "X or Y Rest" clause as short-rest-equivalent.

### Creature Type
- **Prose:** "You are a Humanoid."
- **Expected (current code):** Nothing — there is no "you are a &lt;type&gt;" creature-type detector anywhere in scraper.mjs. This is by design: `assembleRaceItem` (ddb-scraper.mjs:342-346) hardcodes `type: {value: "humanoid", ...}` directly on the race item (the code's own comment: "playable species are Humanoid unless stated otherwise" — a verified-safe default, not a guess), so this trait's text is redundant flavor DDB includes for display purposes only.
- **Actual (compendium data):** `effects: []`. Matches expectation.
- **Gap / verdict:** No real gap — inert stub by design. (Moot for Orc's actual creature type anyway, since Humanoid is correct and would be set by the hardcoded default if a race item existed.)

### Ability Score Increases
- **Prose:** "When determining your character's ability scores, increase one score by 2 and a different one by 1, or increase three scores by 1. None of these increases can raise a score above 20."
- **Expected (current code):** Nothing is built, and this is a real code gap, not staleness. `guessAbilityScoreImprovement` (scraper.mjs:881-910) anchors on `/Increase\s+(?:your|one ability score of your choice|two ability scores of your choice)[^.]*\./i` (line 884) — the word immediately after "Increase" must be "your", "one ability score of your choice", or "two ability scores of your choice" (the feat/half-feat 2024 boilerplate this was verified against, per the function's own comment). This species-level phrasing ("increase one **score** by 2 and a different one by 1, or increase three **scores** by 1") never contains "ability score of your choice", so the sentence match fails and the function returns `null` — no `AbilityScoreImprovement` advancement is ever generated for this trait under current code, for any species.
- **Actual (compendium data):** `advancement: {}`. Consistent with the code gap — would still be empty on a fresh, non-stale re-import.
- **Gap / verdict:** New finding, not staleness, and not Orc-specific — every core 2024 species shares this identical PHB "Ability Score Increases" boilerplate, so this silently drops the ASI grant for all 9 core species' imports alike. Not tracked by any of issues 001-019. The fix is mechanically simple: the "one score by 2 / three scores by 1" species phrasing maps to the exact same `{points: 2, cap: 2, locked: []}` configuration the existing "two ability scores of your choice by 1" feat phrasing already produces (line 899) — only the sentence-anchor regex needs a second alternative.

### Relentless Endurance
- **Prose:** "When you are reduced to 0 Hit Points but not killed outright, you can drop to 1 Hit Point instead. Once you use this trait, you can't do so again until you finish a Long Rest."
- **Expected (current code):** Nothing is built, despite three of the four scanned sub-signals actually firing correctly:
  - `usesFormula`: the bare-"once" detector (scraper.mjs:454-456) fires — "Once you use this trait" contains the literal word "Once", and a long-rest mention is present, so `usesFormula = "1"`.
  - `recoveryPeriod`: correctly resolves to `"lr"` (unambiguous here — only "Long Rest" appears, no "short or" complication like Adrenaline Rush above).
  - `activation`: `TRIGGER_CLAUSE_RE` (line 320) matches at the very start of the segment — "When you are reduced to 0 Hit Points but not killed outright," — captured as `activation.condition`; since no action-economy word (action/bonus/reaction) appears anywhere in the text, `activation.type` falls through to `"special"` (line 334), dnd5e's own catch-all for a triggered-but-not-action-economy ability.
  - But none of `savingThrow`, `diceHints` (heal/damage), `spellNames`, `statusHints`/`toggleStatusHints`, or `effectHints` fire for this text — there is no dice, no condition grant, no resistance/immunity, no sense/speed change, nothing at all for "drop to 1 HP instead of 0" to match. And critically, `guessQueueEntries` (effects-builder.mjs:831-967) never builds an Activity or Effect from `usesFormula`/`recoveryPeriod`/`activation` alone — those three fields only ever get *attached* to an Activity that some other detector (save/damage/heal/cast/toggle-status) independently triggers first. With no such trigger here, all three correctly-detected fields are computed and then simply discarded; nothing is queued.
- **Actual (compendium data):** `effects: []`, `activities: {}`. Matches expectation.
- **Gap / verdict:** Confirmed "no detector covers this" case, and arguably not easily fixable within the current schema-mapping approach: dnd5e has no ActiveEffect change key or first-class Activity shape for "when you'd drop to 0 HP, drop to 1 instead" — this is normally handled with a macro, a custom module flag (e.g. a `midi-qol`-style hook), or manual DM/player bookkeeping, none of which this module currently emits. This is a genuinely new gap, not addressed by (and likely out of scope for) issues 001-019 — worth flagging as a case where the "starting point for review" philosophy may need a dedicated "reaction-to-death-save"-shaped detector, or may simply need to stay a documented limitation.

## Species-level notes

- **Race item absence confirmed for Orc** (`raceItemExists: false`), consistent with the pack-wide finding across all 9 core PHB species (vs. the 7 non-core species — Genasi x3, Warforged, Changeling, Aasimar — which did get race items in the same batch). Static review of `assembleRaceItem`/`buildSizeAdvancement`/`mergeTraitDerivedMovement` (ddb-scraper.mjs) reveals no obvious throw path for a normal Orc `raceDef` shape; `importDdbRace` (importer.mjs:929-963) wraps trait creation and the final race-item creation in one try/catch, so an exception on that last `createItemFromData(assembleRaceItem(...), ...)` call would explain the pattern exactly (each trait is individually `await`ed and committed before the race-item step runs, so traits persist even when the race item's own creation later throws and is only recorded to `report.failed`). None of the per-trait prose gaps found above can throw — they fail closed (null/no-op), so they're not candidates for the actual exception. Root-causing it would need the console/log output from the actual 2026-08-24 run, not available for static review here.
- **Downstream effect of the missing race item:** because `buildSizeAdvancement` and movement/speed both attach only to the race item, Orc currently has no Size advancement and no movement/speed data anywhere in this compendium — not because Speed/Size's detectors are broken (they're inert by design), but because the one item they'd attach to was never persisted.
- **2014/2024 legacy trait mix — the most Orc-specific anomaly:** this import contains **both** "Adrenaline Rush" (the 2024 PHB trait) and "Relentless Endurance" (the 2014-ruleset trait it replaced) in the same species. These are mutually exclusive in official material — a 2024 Orc has Adrenaline Rush, not Relentless Endurance. `usableRacialTraits` (ddb-scraper.mjs:165-169) only filters DDB's racialTraits array on `hideInSheet`; it applies no per-trait ruleset/`isLegacy` filtering at all, and `buildRaceTraitItemData`'s `isLegacy` flag (used only for the `source` field, ddb-scraper.mjs:182-209) is a single value taken from the whole `raceDef`, not evaluated per trait. If D&D Beyond's API response for this race included both trait definitions (e.g. because the account's ruleset/content-toggle setting surfaced a legacy trait alongside the 2024 one, or DDB's own racialTraits array doesn't cleanly separate supplanted traits), this pipeline has no mechanism to detect or drop the superseded one — both get imported side by side with no warning. This is a new finding, not covered by any of issues 001-019, and worth investigating against the actual DDB API payload for Orc (not resolvable by source review alone) since it would silently double up mutually-exclusive traits for any species with a similar 2014→2024 replacement (e.g. Half-Orc/Orc, Tiefling's legacy vs. 2024 trait sets).
- **Cross-species implication:** the Ability Score Increases gap is structural, not Orc-specific, and reproduces identically for Human, Elf, Dwarf, Halfling, Gnome, Dragonborn, Tiefling, and Goliath — none of the core species' ASI grants would import correctly even on a fresh, non-stale run today.
