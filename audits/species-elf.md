# Species Audit: Elf

## Summary

No `race`-type Item exists for Elf (`raceItemExists: false`), consistent with the cross-species finding that all 9 core PHB 2024 species failed to get a race item while 7 non-core species succeeded. All 10 Elf trait items have completely empty `effects`/`activities`/`advancement` — the raw placeholder shape `buildRaceTraitItemData` initializes (`scripts/ddb-scraper.mjs:182-209`), not "scanned and found nothing." This is consistent with the import (2026-08-24 ~16:52 UTC) predating every commit that wires `buildAutoMechanics`/proficiency/ASI detection into the species import path (all dated 2026-08-25). Re-running the import today (current working tree, which — note — already contains uncommitted code for issues 016-019 even though those issue files/tests are themselves uncommitted) would fix **Darkvision** (a correct sense-upgrade effect) and **Keen Senses** (a correct skill-choice `Trait` advancement), but **8 of 10 traits would still come out empty even under current HEAD**, and one trait — **Elven Lineage** — would come out actively *wrong*: its HTML table folds all three lineages (Drow/High Elf/Wood Elf) into one undifferentiated text blob, which a live probe against the real description HTML confirms produces a spurious `system.attributes.movement.walk` upgrade to 35 ft (Wood Elf's own bonus) that would be granted to every Elf regardless of chosen lineage, while none of the table's nine cantrip/spell names (Dancing Lights, Prestidigitation, Druidcraft, Faerie Fire, Darkness, Detect Magic, Misty Step, Longstrider, Pass without Trace) are recognized at all. **Fey Ancestry** and the species' own **Ability Score Increases** trait — arguably Elf's two most mechanically important traits — are also both complete, previously-undocumented misses.

## Traits

### Fey Ancestry
- **Prose:** "You have Advantage on saving throws you make to avoid or end the Charmed condition."
- **Expected (current code):** Nothing. Verified directly with `scanSegmentText` against this exact text — every field of the result (`savingThrow`, `effectHints`, `statusHints`) comes back null/empty. `savingThrow` requires an explicit `<Ability> saving throw` phrase (`scripts/scraper.mjs:460`); this text names no ability. The condition-immunity detector only fires when `/\bimmun(?:e|ity)\b/i` matches somewhere in the segment (`scripts/scraper.mjs:611`); "Advantage" never trips that gate, so the "Charmed condition" mention is never even scanned for immunity. There is no detector anywhere in this codebase for "advantage on saving throws" as its own category — confirmed by grepping `scraper.mjs`/`effects-builder.mjs`/`ddb-scraper.mjs` for "advantage": the only hit is an unrelated guard-clause comment in issue 019's markdown, not a code path.
- **Actual (compendium data):** Empty, matches expected.
- **Gap / verdict:** Genuine, previously-undocumented gap, not staleness. This is not a case of "immunity" and "advantage-on-saves" being confused with each other (the audit brief's suggested angle) — it's a full miss, because no detector for advantage-granting language exists at all, in either direction. Not covered by any of issues 001-019. Worth its own issue: a `save advantage against <condition>` detector would need to build an ActiveEffect with `flags.dnd5e.saveAdvantage.<ability_or_all>` or a per-condition equivalent, a change key this scanner has never produced before.

### Darkvision
- **Prose:** "You have Darkvision with a range of 60 feet."
- **Expected (current code):** Matches. `darkvisionMatch` (`scripts/scraper.mjs:752-757`) recognizes the "Darkvision with a range of 60 feet" connector shape directly, producing `effectHints: [{ key: "system.attributes.senses.darkvision", mode: 4 (upgrade), value: "60" }]`. `guessQueueEntries` (`scripts/effects-builder.mjs:900-913`) turns this into a permanent, `transfer: true` ActiveEffect. Verified live against `scanSegmentText`.
- **Actual (compendium data):** Empty (stale — predates the commits that wire this into species import).
- **Gap / verdict:** Pure staleness. A fresh reimport on current HEAD would correctly attach this effect.

### Size
- **Prose:** "You are Medium (about 5–6 feet tall)."
- **Expected (current code):** Nothing from this trait *item* — no detector in `scanSegmentText` matches "You are Medium..." phrasing. The real Size mechanic is meant to live on the *race item* via `buildSizeAdvancement` (`scripts/ddb-scraper.mjs:248-265`, keyed off `raceDef.sizeId`, not trait prose), which is species-level, not per-trait.
- **Actual (compendium data):** Empty, matches expected (correctly inert regardless of code version).
- **Gap / verdict:** No gap on the trait item. The actual mechanic never got attached anywhere because the race item itself was never created (finding #1) — for Elf specifically this happens to be low-impact, since dnd5e's own built-in default size is already Medium.

### Elven Lineage Spells
- **Prose:** "When you choose your Elven Lineage, and at character levels 3 and 5, you learn a spell as shown on the table. You always have that spell prepared. You can cast it once without a spell slot, and you regain the ability to cast it in that way when you finish a Long Rest. You can also cast the spell using any spell slots you have of the appropriate level. Intelligence, Wisdom, or Charisma is your spellcasting ability..."
- **Expected (current code):** Nothing. Verified live: `scanSegmentText` correctly detects `recoveryPeriod: "lr"` (Long Rest mention) and `usesFormula: "1"` (bare "once," gated on the rest mention per issue 016) and even `activation: { type: "special", condition: "When you choose your Elven Lineage" }` (issue 017's leading-trigger-clause detector, `scripts/scraper.mjs:320`) — but none of these three ever gets attached to an actual queue entry, because `guessQueueEntries` (`scripts/effects-builder.mjs:831-967`) only threads `usesFormula`/`recoveryPeriod`/`activation` onto an entry it's already building from a saving throw, dice hint, or *named* spell — and this trait names no spell at all in its own text (the name comes from a table on the sibling "Elven Lineage" trait, referenced only as "a spell as shown on the table"). No detector here can resolve a table cross-reference between two separate Feature items.
- **Actual (compendium data):** Empty, matches expected.
- **Gap / verdict:** Genuine gap, not staleness — even on current HEAD this stays empty. This is a structural limitation (DDB splits "you get a spell, mechanically" from "here's which spell" across two trait items with no explicit link between them), not a phrasing tweak; not covered by issues 001-019.

### Elven Lineage
- **Prose:** "You are part of a lineage that grants you supernatural abilities. Choose a lineage from the Elven Lineages table. You gain the level 1 benefit of that lineage. When you reach character levels 3 and 5, you learn a higher-level spell, as shown on the table... [table: Drow → Darkvision to 120 ft + Dancing Lights cantrip, then Faerie Fire/Darkness; High Elf → Prestidigitation cantrip (swappable), then Detect Magic/Misty Step; Wood Elf → Speed to 35 ft + Druidcraft cantrip, then Longstrider/Pass without Trace]"
- **Expected (current code):** **Wrong, not just incomplete** — verified with a direct probe reproducing the module's own segmentation and scan logic against this trait's real description HTML. `guessFeatureMechanics` (`scripts/scraper.mjs:833-865`) splits prose into segments at top-level block elements, starting a new segment only when a block opens with a `<strong>`/`<b>` label (`leadingBoldLabel`, `scripts/scraper.mjs:193-206`). This trait's three `<p>` tags and its one `<table>` all lack a leading bold tag — the "Drow"/"High Elf"/"Wood Elf" row headers are plain `<td>` text, not `<strong>` — so all four blocks collapse into a **single** unlabeled segment, and the table's cell text is flattened via `textContent` into one undifferentiated string with no per-lineage boundary. Running `scanSegmentText` on that exact flattened text produces:
  - `effectHints: [{ key: "system.attributes.movement.walk", mode: 4, value: "35" }]` — the Wood Elf-only "Your Speed increases to 35 feet" line (matched by `speedToMatch`, `scripts/scraper.mjs:724-728`) with no lineage qualifier, so `guessQueueEntries` would build this as a permanent, unconditional effect attached to the whole "Elven Lineage" item — granted to every Elf regardless of which lineage (or none) they actually pick.
  - `spellNames: []` — none of the nine spell/cantrip names in the table are recognized. The two "you also know the `<X>` cantrip" phrasings (Dancing Lights, Druidcraft; and the standalone "You know the Prestidigitation cantrip") fail because `castRe`'s trailing optional group only recognizes a literal "spell" suffix (`scripts/scraper.mjs:422`, `(?:spell)?`), not "cantrip" — so the capture swallows "cantrip" itself into the candidate name (e.g. "Dancing Lights cantrip"), which then fails the exact-name index lookup. The six level-3/5 spell names (Faerie Fire, Darkness, Detect Magic, Misty Step, Longstrider, Pass without Trace) sit in the table with no leading verb at all, so they're never even candidates.
  - `usesFormula`/`recoveryPeriod`/`activation` are computed (same dead-data pattern as Elven Lineage Spells above) but never attached to anything, since no spellNames/savingThrow/diceHints exist to anchor them to.
- **Actual (compendium data):** Empty (stale).
- **Gap / verdict:** Two stacked, previously-undocumented gaps, both surviving on current HEAD: (1) the segmenter has no way to split a feature's sub-choices when they're presented as a table with plain-text row headers rather than bold-labeled paragraphs — a structurally different case from the `leadingBoldLabel` convention this scanner was built around; (2) the spell/cantrip-name detector's suffix handling only covers "spell," not "cantrip," a real and common D&D Beyond phrasing (also likely affects other species/feats granting a fixed cantrip). Neither is covered by issues 001-019. Given #1 would actively mis-attribute a lineage-specific bonus to the wrong (or every) character, this is the single most consequential finding in this audit — worse than a silent miss.

### Creature Type
- **Prose:** "You are a Humanoid."
- **Expected (current code):** Nothing from the trait's own prose — there is no creature-type detector anywhere in `scanSegmentText`. `assembleRaceItem` unconditionally hardcodes `system.type.value: "humanoid"` on the race item itself (`scripts/ddb-scraper.mjs:342-346`), independent of this trait's text.
- **Actual (compendium data):** Empty, matches expected.
- **Gap / verdict:** No gap on the trait item — correctly inert flavor text. The actual mechanic lives on the (missing) race item.

### Ability Score Increases
- **Prose:** "When determining your character's ability scores, increase one score by 2 and a different one by 1, or increase three scores by 1. None of these increases can raise a score above 20."
- **Expected (current code):** No ASI advancement is produced. `guessAbilityScoreImprovement` (`scripts/scraper.mjs:881-910`) anchors its sentence-extraction on `Increase\s+(?:your|one ability score of your choice|two ability scores of your choice)` (`scripts/scraper.mjs:884`) — feat/Epic-Boon boilerplate phrasing. This species-level trait's actual wording — "increase **one score** by 2 and a different one by 1, or increase **three scores** by 1" — never contains any of those literal substrings ("your" doesn't appear at all; it's "one score," not "one ability score of your choice"), so the regex match is `undefined` and the function returns `null`. Verified live (`guessAbilityScoreAdvancement` → `null`). `guessProficiencyAdvancement` also doesn't apply (no proficiency/training/language language present).
- **Actual (compendium data):** Empty.
- **Gap / verdict:** Genuine detector gap, not staleness — even on current HEAD this trait produces nothing. Issue 009 only wired the *existing* ASI detector into `buildAutoMechanics`; it never extended the detector's phrasing coverage to species-level ASI text, which is a materially different sentence shape from every feat-level phrasing it was written against. Not covered by any of issues 001-019. Since this exact "increase one score by 2 and a different one by 1, or increase three scores by 1" sentence is D&D Beyond's standard 2024 species-ASI boilerplate (not Elf-specific wording), this almost certainly means **every** DDB-imported 2024 species silently gets no ability-score-increase advancement at all — one of the highest-impact gaps found in this audit.

### Trance
- **Prose:** "You don't need to sleep, and magic can't put you to sleep. You can finish a Long Rest in 4 hours if you spend those hours in a trancelike meditation, during which you retain consciousness."
- **Expected (current code):** Nothing. Verified live: `recoveryPeriod` is detected as `"lr"` (Long Rest mention, `scripts/scraper.mjs:432-436`), but `usesFormula` stays `null` — the bare once/twice detector (issue 016) requires the literal word "once" or "twice" in the segment, and this text has neither. No entry is ever built from a bare `recoveryPeriod` alone. Separately, "magic can't put you to sleep" never trips the immunity regex (no "immune"/"immunity" word present, same gap category as Fey Ancestry above), and there is no detector anywhere for an altered/shortened rest duration ("finish a Long Rest in 4 hours" — no "reduced rest time" mechanic key exists in this codebase at all).
- **Actual (compendium data):** Empty, matches expected.
- **Gap / verdict:** Two independent misses, both new: sleep-immunity uses non-"immune" phrasing (same root cause as Fey Ancestry's advantage-language gap — a defensive trait described without the trigger keyword this scanner keys on), and reduced-long-rest-duration has no detector at all. Low practical impact (dnd5e core doesn't track "needs sleep" as a rollable stat, and 4-hour Long Rests are a house-rule-adjacent variant most tables track manually anyway), but worth documenting as a real, reproducible gap rather than "working as intended."

### Speed
- **Prose:** "Your speed is 30 feet."
- **Expected (current code):** Nothing. None of `scanSegmentText`'s three speed regexes match a flat "is 30 feet" statement — they require either a delta ("speed increases by/to N feet," `scripts/scraper.mjs:712,724`) or an absolute grant phrased as "you have a `<type>` speed of N feet" (`scripts/scraper.mjs:736`). "Your speed is 30 feet" matches neither shape.
- **Actual (compendium data):** Empty, matches expected.
- **Gap / verdict:** No gap on the trait item — base walking speed for a species is meant to come from `raceDef.weightSpeeds?.normal` / `mergeTraitDerivedMovement` on the race item (`scripts/ddb-scraper.mjs:324-326`), not from this flavor-restating trait's own prose. Only "missing" here because the race item itself doesn't exist (finding #1); for Elf the value (30 ft) coincides with dnd5e's own default anyway, so the practical impact is nil.

### Keen Senses
- **Prose:** "You have proficiency in the Insight, Perception, or Survival skill."
- **Expected (current code):** Matches, correctly. `guessProficiencyAdvancement`'s clause regex (`scripts/scraper.mjs:957`) captures "the Insight, Perception, or Survival skill," and `parseProficiencyClause` (`scripts/scraper.mjs:1094-1161`) — since the clause has "or" but no "and" — treats it as a choice list (`isChoiceList`, `scripts/scraper.mjs:1141-1143`) rather than unconditional grants, resolving each name through `skillCode` (which strips the trailing "skill" wrapper, `scripts/scraper.mjs:995`). Verified live: produces a `Trait` advancement with `configuration.choices: [{ count: 1, pool: ["skills:ins", "skills:prc", "skills:sur"] }]`, exactly the correct shape.
- **Actual (compendium data):** Empty (stale).
- **Gap / verdict:** Pure staleness. A fresh reimport on current HEAD would correctly populate this trait's advancement.

## Species-level notes

**Race item absence (finding #1).** No `race`-type Item was created for Elf. `importDdbRace` (`scripts/importer.mjs:929-963`) unconditionally attempts `assembleRaceItem`/`createItemFromData` for every species with no core-vs-non-core branch anywhere in the current code, so this can't be explained by a deliberate skip in the current pipeline — it's an exception or early-exit that happened during the actual (now-stale, pre-08-25) import run. Since the trait-creation loop runs *before* the race item's own creation inside the same `try` block, a failure there would explain "10 real trait items exist, but the race item silently never got created, and the whole species import continues to the next race." I could not identify a code-level reason in the *current* `assembleRaceItem`/`buildSizeAdvancement`/`mergeTraitDerivedMovement` that would throw for Elf specifically, and none of the 10 core-species-vs-7-non-core-species candidate fields (`fullName`, `sizeId`, `weightSpeeds`) are handled differently in the current code — this is worth a live re-import test rather than further static analysis, since it may simply no longer reproduce.

**Consequence of the missing race item beyond Size/Speed/Creature Type.** The far bigger practical loss is `buildRaceAdvancement`'s `ItemGrant` (`scripts/ddb-scraper.mjs:218-232`), which is what would auto-attach all 10 trait items to a PC's sheet when they pick "Elf" as their species. With no race item at all, a GM must manually drag all 10 Feature items onto a character one at a time — this is a bigger day-to-day usability gap than any single trait-level detector miss above.

**Lineage/subrace choice handling.** D&D Beyond's 2024 Elf models Drow/High Elf/Wood Elf as a single "Elven Lineage" trait with an embedded choice table, not as separate sub-race entities the way 2014-rules subraces (or this pack's own Genasi variants) are modeled as distinct top-level race definitions. Nothing in `ddb-scraper.mjs`/`importer.mjs` represents an in-trait player choice as a dnd5e `ItemChoice`/`ItemGrant` advancement — the whole table is just baked into one Feature item's description, and (per the Elven Lineage finding above) the auto-mechanics scanner actively misreads part of that table as an unconditional grant. A correct import would need either a real per-lineage choice mechanism or, at minimum, for the auto-mechanics scanner to recognize a table and refuse to guess across its rows rather than flattening them together.
