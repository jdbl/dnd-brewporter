  refreshProxyStatus() closure that both the initial render and the link's
  click handler call. No change to checkProxyHealth() or the proxy itself,
  both of which were confirmed already correct. node --check passed
  (had to use the nvm-managed node directly — plain `node` isn't on PATH in
  the sandboxed shell here, unrelated to the module).
  Not yet re-verified inside a live Foundry client (still blocked on V4 for

- 2026-08-19 — session 3 (cont'd again) — User came back with a real
  "Publish to web" doc URL (`docs.google.com/document/d/e/2PACX-.../pub`)
  that genuinely failed — this was NOT just a bad link like the earlier
  false alarm. Fetched it directly and found two separate real bugs, both
  fixed:
  1. resolveSourceUrl() (scraper.mjs) — the `/d/e/<id>/` pattern is a
     different, opaque ID scheme from a normal `/d/<id>/edit` link, but the
     old regex matched the "e" as if it were a normal doc ID, producing a
     broken `.../document/d/e/export?format=html` URL (404s). Fixed by
     checking for the `/d/e/` pattern first and, for that case, returning
     the `/pub` URL unchanged — published docs are ALREADY the plain
     fetchable HTML page, no `/export` rewrite needed or possible.
  2. freeform-scraper.mjs's root-element selection — a normal
     export?format=html page has its content as direct children of <body>
     (which itself carries the class "doc-content"), but a /pub page nests
     the same per-paragraph markup inside `<div id="contents"><div
     class="... doc-content">` — several levels deeper. The scraper only
     ever looked at `doc.body.children` (top level only, no recursion by
     design), so it saw nothing and would throw "Could not find any
     readable text". Fixed by scanning `doc.querySelector(".doc-content")
     ?? doc.body` instead — resolves to <body> itself for the export-html
     case (same class is present there) and to the correct nested div for
     the /pub case, verified by inspecting both real fixtures' DOM
     structure directly.
  Also found and fixed a third, more subtle bug while verifying against
  this new real fixture: the title-line detection assumed the title block
  is always exactly 2 lines (name, then "A X Subclass" tagline) — true for
  Oath of Love, but this doc's title block is 3 lines ("Otherworldly
  Patron:" / "The Dragon" / "A Warlock Subclass"), so the old code grabbed
  "Otherworldly Patron:" as the name and never even looked at the 3rd line
  for the tagline (classIdentifier came out null). Since this doc's feature
  headings are unambiguous, confidence (6) was well above the review
  threshold (2), so this would have silently created a subclass named
  "Otherworldly Patron:" with no review step to catch it — worse than an
  outright failure. Fixed by buffering every substantial line seen before
  hitting *either* a tagline match or the first level-heading; on a tagline
  match, name = whichever buffered line came immediately before it (not
  necessarily line 1); with no tagline ever found, falls back to the old
  "first line = name" behavior. Verified against both fixtures side by
  side: Oath of Love's name/classIdentifier/confidence/featuresByLevel are
  byte-identical to before (no regression), and the Dragon doc now comes
  out as name="The Dragon", classIdentifier="warlock", confidence=6, with
  all 4 level/6 feature pairs correct. Full existing regression suite
  (12 classes + 3 subclasses + Artificer + integration test) still passes.
  README updated to document that both Google Docs link types are
  supported and why they need different handling.

- 2026-08-19 — session 2 — User reported that freeform-sourced homebrew
  features (e.g. "Loving Embrace" in Oath of Love's Channel Divinity) were
  failing to resolve — correctly, since they're original content with no
  compendium equivalent to look up at all, unlike wikidot features which
  always reference something real. Root cause: freeform-scraper.mjs was
  capturing feature *names* for the ItemGrant but discarding all the prose
  that followed each heading — the actual mechanical text was being thrown
  away entirely, not just left unresolved.
  Fix: freeform-scraper.mjs now tracks each detected heading as an "active
  feature" and accumulates every block between it and the next heading (or
  end of doc) into that feature's own `descriptionHtml`, returned as a new
  `featureDetails: [{level, name, descriptionHtml}]` array alongside the
  existing `featuresByLevel` (kept as-is for the review dialog and
  confidence calc, which only care about names). importer.mjs's
  handleFreeformResult() now creates a real `type: "feat"` Item for each
  feature it has captured prose for (schema verified against dnd5e's own
  shipped Disciple of Life source — `system.type.value: "class"` is used
  for both class AND subclass features, no separate subtype), and passes
  its real UUID straight into the subclass's ItemGrant — no FIXME, no
  lookup needed. scraper.mjs's buildSubclassAdvancement() was extended
  (backward compatible) to accept either a bare name string (wikidot path —
  unchanged, still produces a FIXME/lookup placeholder) or a `{name, uuid}`
  pair (freeform path — uuid already real). Spells inside "Oath Spells"
  etc. are untouched by this — those genuinely are real PHB spells and
  still go through normal compendium lookup, only each subclass's own named
  features get auto-generated as new items.
  Verified: re-ran the full integration test — the report now shows 5 real
  generated Feature items for Oath of Love (Oath Spells, Channel Divinity,
  Aura of Love, Empowered by Love, Knight of Hearts), confirmed the
  Channel Divinity item's description literally contains "Loving Embrace"
  and "Galvanizing Affection" in full, confirmed the subclass's own
  ItemGrant entries hold real UUIDs with no FIXME hint field, and confirmed
  the "Unresolved" report section now only lists the real spells (Bless,
  Haste, ...) that still need compendium lookup — the homebrew features no
  longer appear there at all. Full regression suite (12 classes + 3
  subclasses + Artificer) still passes unchanged.
  Edge case documented but not fully solved: if a low-confidence freeform
  parse goes through manual review and the user renames a detected feature,
  the renamed row won't match its captured description (matched by exact
  level+name) and falls back to the normal FIXME/lookup path instead —
  acceptable given that path is already the "more manual" tier.
