- 2026-08-19 — session 3 (cont'd again) — User came back with a real
  "Publish to web" doc URL (`docs.google.com/document/d/e/2PACX-.../pub`)
  that genuinely failed — this was NOT just a bad link like the earlier
  false alarm. Fetched it directly and found two separate real bugs, both
  fixed:
  1. resolveSourceUrl() (scraper.mjs) — the `/d/e/<id>/` pattern is a
     different, opaque ID scheme from a normal `/d/<id>/edit` link, but the
     old regex matched the "e" as if it were a normal doc ID, producing a
     broken `.../document/d/e/export?format=html` URL (404s). Fixed by
     checking for the `/d/e/` pattern first and, for that case, returning
     the `/pub` URL unchanged — published docs are ALREADY the plain
     fetchable HTML page, no `/export` rewrite needed or possible.
  2. freeform-scraper.mjs's root-element selection — a normal
     export?format=html page has its content as direct children of <body>
     (which itself carries the class "doc-content"), but a /pub page nests
     the same per-paragraph markup inside `<div id="contents"><div
     class="... doc-content">` — several levels deeper. The scraper only
     ever looked at `doc.body.children` (top level only, no recursion by
     design), so it saw nothing and would throw "Could not find any
     readable text". Fixed by scanning `doc.querySelector(".doc-content")
     ?? doc.body` instead — resolves to <body> itself for the export-html
     case (same class is present there) and to the correct nested div for
     the /pub case, verified by inspecting both real fixtures' DOM
     structure directly.
  Also found and fixed a third, more subtle bug while verifying against
  this new real fixture: the title-line detection assumed the title block
  is always exactly 2 lines (name, then "A X Subclass" tagline) — true for
  Oath of Love, but this doc's title block is 3 lines ("Otherworldly
  Patron:" / "The Dragon" / "A Warlock Subclass"), so the old code grabbed
  "Otherworldly Patron:" as the name and never even looked at the 3rd line
  for the tagline (classIdentifier came out null). Since this doc's feature
  headings are unambiguous, confidence (6) was well above the review
  threshold (2), so this would have silently created a subclass named
  "Otherworldly Patron:" with no review step to catch it — worse than an
  outright failure. Fixed by buffering every substantial line seen before
  hitting *either* a tagline match or the first level-heading; on a tagline
  match, name = whichever buffered line came immediately before it (not
  necessarily line 1); with no tagline ever found, falls back to the old
  "first line = name" behavior. Verified against both fixtures side by
  side: Oath of Love's name/classIdentifier/confidence/featuresByLevel are
  byte-identical to before (no regression), and the Dragon doc now comes
  out as name="The Dragon", classIdentifier="warlock", confidence=6, with
  all 4 level/6 feature pairs correct. Full existing regression suite
  (12 classes + 3 subclasses + Artificer + integration test) still passes.
  README updated to document that both Google Docs link types are
  supported and why they need different handling.
